# 实现 Plan 共用机制

本文件不是独立任务入口。当某个 workflow 声明进入实现 Plan、补 Plan，或引用本文件时，**必须先完整加载本文件**，再与该 workflow 中的分级条件、Plan 字段语义一并执行。

分级条件（何时必须 / 可跳过 Plan）与 Plan 正文字段的业务含义，由引用方 workflow 定义。本文件约定载体、阶段入口选择（P-A / P-B）、软提示、确认门禁与中途叫停。

前置阶段未完成时的硬拦（不得编码、不得出实现类 Plan）见总纲「需求澄清」与引用方阶段一，本文件不提供豁免。

## Plan 载体与落盘（S1）

- **默认载体是当前对话**：输出可审阅的 Plan 正文，等待用户确认即可。不强制切换任何 IDE 的 Plan Mode，不强制写入仓库或本地文件。
- **禁止擅自落盘**：未经用户明确要求，不得把 Plan 写成项目文件。
- **持久化由用户发起**：用户明确要求保存时才落盘；保存路径由用户指定，或由 Agent 给出可选项并标明推荐项后等用户选定。业务可用 `ai-engineering-overlay/` 加严落盘规则；本机制不规定唯一目录。
- **禁止**把业务实现 Plan 写入 `ai-engineering-specs/`（规范正文目录只放规范，不放过程产物）。

## 阶段入口选择（G1：P-A / P-B）

仅当同时满足时适用本段：

- 引用方前置阶段已完成（未决 / 基线与范围等已确认）。
- 引用方已判定**必须出 Plan**（不属于可自动跳过 Plan）。

此时必须**停在阶段入口**，不得自动输出 Plan 正文，也不得编码。必须给出且仅给出以下两档，并标明推荐项，等待用户选定：

| 选项 | 含义 |
|------|------|
| **P-A（推荐）** | 先出实现 Plan（引用方规定的标准五字段，精炼可执行，非另一档「详细 Plan」），用户确认后再实现 |
| **P-B** | 跳过 Plan，按已定细节直接实现；交付必须注明「用户选择跳过 Plan」 |

本规范只有上述一档实现 Plan，不区分「短 Plan / 详细 Plan」。

说明要点（可写入同一条回复，但仍须等待选定）：

- 当前已进入「实现 Plan」阶段入口，需用户选择后再继续。
- 即使用户此前要求过「直接实现 / 别问那么多」，仍须完成本选择；不得因早先口头要求而跳过本入口。

执行规则：

- 用户选 **P-A**：再进入「环境软提示」与「Plan 确认门禁」，输出 Plan 正文并等待确认；**选定 P-A 之前不得输出 Plan 正文**。
- 用户选 **P-B**：进入引用方编码 / 改码阶段；本轮不再劝说改回 P-A。
- 用户未选定前不得编码、不得输出 Plan 正文，也不得擅自当作已选 P-A 或 P-B。
- 用户在本入口说「直接实现 / 不要 Plan」：视为倾向 P-B，但仍须其明确选定 P-A 或 P-B（可再确认一句），不得直接开写。**本条仅适用于尚未输出 Plan 正文的本入口**；Plan 正文已输出后的同类说法见「Plan 确认门禁」，不得套用本条的「倾向 P-B」。
- **不适用**：引用方已判定可自动跳过 Plan 的任务（按引用方跳过规则直接编码即可，不必问 P-A / P-B）。
- **不适用**：前置阶段未完成（走总纲与引用方硬拦，不提供 P-A / P-B，也不提供跳过未决）。

## 环境软提示（T1）

仅在用户已选定 **P-A**、即将输出 Plan 正文时，按当前对话环境可附一句说明（可选，不是门禁）：

- **默认**：请在本对话审阅并确认下方 Plan。
- **勿提示**「切换到 Plan Mode 可审阅当前对话中的 Plan」（Cursor Plan Mode 不会承接对话里已有正文）。
- 若用户希望改用 Cursor Plan Mode 另行生成方案，可说明那是另一条路径，与本对话 Plan 不是同一份。

## Plan 确认门禁

- 用户已选定 P-A 后：按引用方规定的字段输出 Plan，等待用户确认；未确认前不得写实现代码。确认以用户明确回复为准，不依赖是否切换 Mode、是否落盘。
- 用户确认 Plan 后，仅按确认版 Plan 进入引用方的编码 / 改码阶段。
- **视为确认**：用户明确认可当前 Plan 正文的回复，例如「确认」「确认 Plan」「同意这份 Plan」「确认 Plan 并实现」。「确认 Plan 并实现」视为确认 Plan 且进入编码，不视为跳过 Plan。
- **不算确认（硬拦）**：Plan 正文已输出后，用户仅说「直接实现」「开始写」「别问了」「开干」等、且未明确认可当前 Plan 正文时，**不视为确认**，也不得当作改选 P-B 或「已确认并实现」。必须停止写码，再次给出可选项并标明推荐项，等待选定后再继续。可选项至少包括：
  - **确认 Plan 并实现（推荐）**
  - **修改 Plan 后再确认**（由用户说明要改的点）
- **阶段区分**：G1「直接实现 → 倾向 P-B」只适用于尚未输出 Plan 正文时；一旦已输出 Plan 正文，只适用本门禁。
- 用户已选定 P-B 的，不走本门禁，直接进入编码 / 改码。

## 中途叫停与补 Plan

用户在编码或改码过程中以任意明确语义要求暂停并先对齐实现方案时（例如「停，先补 Plan」「暂停开发，出实现方案」），执行本段，优先级高于继续改码。

1. **立即停止编码**，不再继续改文件。
2. **盘点现状**：已改/已创建的文件、当前进度、与目标的差距。
3. **补一份实现 Plan**（标准五字段；不再次询问 P-A / P-B）。Plan 字段语义遵循引用方 workflow；载体与落盘遵循本节 S1。若已有改动，Plan 中必须另列「已改代码处理」三项可选项（针对叫停前已产生的代码改动），并标明推荐项：
   - **保留继续**：已有改动全部保留，按确认版 Plan 接着做。
   - **回滚重做**：撤销叫停前相关改动后，按确认版 Plan 重做。
   - **局部调整**：保留仍符合目标的已改内容，修正或删除不符合的部分，再按确认版 Plan 继续；确认版 Plan 须写明保留 / 修改 / 删除的范围。
4. **等待用户确认** Plan 及「已改代码处理」选项；未确认前不得继续写实现代码，也不得擅自回滚或继续改。
5. **确认后**按确认版 Plan 与所选处理方式继续；交付时注明「中途叫停补 Plan」及最终处理方式。

中途叫停以补 Plan 为准：不适用 P-B 跳过本次补 Plan。

## 共用禁止动作

- 未经用户明确要求擅自将 Plan 落盘，或把业务 Plan 写入 `ai-engineering-specs/`。
- 将切换 Plan Mode 或落盘当作确认门禁（未切换、未落盘不得拒绝在对话中完成 Plan 确认）。
- 中途叫停后，在用户未确认前擅自回滚、继续改，或跳过补 Plan。
- 在必须出 Plan 时，未完成阶段入口 P-A / P-B 选定就输出 Plan 正文或编码，或擅自当作已选 P-A / P-B。
- Plan 正文已输出后，将「直接实现」「开始写」「别问了」「开干」等未明确认可 Plan 的说法当作已确认并编码，或当作改选 P-B。
- 在前置阶段未完成时，以「直接实现」「先出 Plan」或任何跳过未决的说法放行。
