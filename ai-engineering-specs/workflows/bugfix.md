# 缺陷修复标准作业流程 (SOP)

## 进入条件

- 用户任务命中本流程的索引触发项。
- 目标是纠正已有行为，而不是新增能力。

## 阶段一：复现

1. 记录期望行为与实际行为。
2. 尝试用现有入口、测试或最小脚本复现。
3. 能复现时，保留复现步骤和结果，进入阶段二。

## 无法直接定因

Agent 无法自行复现，或复现结果不足以确定原因时，改为人工辅助取证，不得按猜想改业务代码：

1. Agent 在关键路径增加日志，日志要能区分候选原因。
2. 请人工按原路径复现，并把日志回传。
3. Agent 根据回传日志分析，确认原因后再进入方案选择。
4. 日志尚未回传时，停止修复。

## 阶段二：确认原因

1. 列出候选原因。
2. 用复现结果、日志或失败测试排除未证实的候选。
3. 写下已确认的原因，以及它对应的证据。

## 阶段三：选择修复范围

原因确认后先停止改代码，向用户给出两个方案，并允许用户自定义范围。用户选定前不得开始修复。

1. **最小修复**：只改与已确认原因直接相关的代码，让当前错误路径恢复预期行为。
2. **长期维护修复**：在确认原因的前提下，按专业规范整理同类路径，补上能防止复发的结构和回归检查。

标明推荐项。影响面只在当前一处时，推荐最小修复。同一原因会在同类路径重复出现时，推荐长期维护修复。

## 阶段四：实施与回归

1. 只实施用户选定的方案。
2. 用原复现步骤或新增回归检查验证期望行为。
3. 交付时写明原因、证据、所选方案、改动和验证结果。

## 禁止动作

- 没有复现结果、也没有日志证据时直接改代码。
- 日志已加上但人工尚未回传时继续改业务逻辑。
- 把多个未证实的猜想一起改掉。
- 未等用户选择修复范围时，直接按最小修复改代码。

## 完成标准

- 原因已写明，并对应到复现结果或人工回传的日志。
- 修复范围来自用户的选择。
- 原问题路径已再验证，或写明当前环境无法执行的验证项。
